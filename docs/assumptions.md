# Assumptions Log

**Owner:** Product Analyst, Growth · **Last updated:** 2026-11-03

Every assumption behind the numbers in this project is listed here, one per row: what we assumed, why (or where it comes from), what changes if it is wrong, and how to check it. The IDs are referenced from [`02_metric_definitions.md`](02_metric_definitions.md), [`readout.md`](readout.md) and `config.yaml`. Rows that set a parameter name the `config.yaml` key.

## Check these first

These five are the most likely to change a decision.

| ID | Why it matters |
|---|---|
| **B1, B2** | Value per conversion and the actual CPM decide whether the campaign *pays*. Today we can only state a breakeven threshold. |
| **A1** | The ad experiment's 96/4 allocation is inferred, not documented, so its SRM "pass" is weak evidence. |
| **C5** | The gate experiment's split gives an SRM WARNING. The gate result cannot be certified until assignment is explained. |
| **A7** | Without dates we cannot check novelty effects, test duration or seasonality. |
| **A5** | The conversion event is undocumented, so we don't know what a "conversion" is worth. |

## A. Ad experiment (Marketing A/B)

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| A1 | The intended allocation was **96% ad / 4% PSA** (`intended_ad_share: 0.96`). | Not documented in the data source. Inferred from the observed split (96.00% / 4.00%), which is suspiciously round. | The SRM check (p = 0.9998) only confirms a ratio we read off the same data. If the design was, e.g., 95/5 or 90/10, the observed split would be a large mismatch and the result could not be certified. | Get the experiment config or brief from the ad platform / Eng and compare it with the assignment logs. Until then, rely on exposure parity: mean ads per user are 24.82 vs 24.76 (M13). |
| A2 | Assignment was random at the user level and fixed for the whole flight (no re-assignment, no switching arms). | Standard for a PSA-holdout design. `user id` is unique (588,101 rows, 0 duplicates). | Self-selection or arm switching would bias the lift in an unknown direction. | Assignment logs should show one assignment event per user, made before first exposure. |
| A3 | Users are independent: no interference between arms, and one person = one `user id`. | The user is the unit of analysis; the data has no household or device keys. | Spill-over (e.g. ad-arm users influencing PSA-arm users) shrinks the measured lift. One person under several IDs overstates precision. | De-duplicate by device / login and measure the share of people with several IDs. If spill-over is plausible, randomize in clusters. |
| A4 | The file contains every user who was *served* at least one ad slot, with the same inclusion rule in both arms. | `total ads` ≥ 1 for every row (min = 1). | If one arm lost users differently (e.g. ad blockers affect real ads but not PSAs), the denominators differ and the lift is biased. | Reconcile assigned vs served users per arm against the ad server. |
| A5 | `converted` is a yes/no flag per user for one business event (e.g. purchase or sign-up; not documented). It is measured the same way in both arms and counted at most once per user. | The only values are `True` / `False`; the data has no event name and no counts. | The value per conversion (B1) could be off by an order of magnitude. Repeat conversions are invisible, so impact is undercounted if ads drive repeat purchases. | Check the tracking plan / event dictionary with the data owner, and whether upstream has more than one conversion per user. |
| A6 | Only conversions after assignment and within the experiment window are counted. | Standard for an experiment outcome; there are no timestamps to check it. | Pre-exposure conversions would dilute the lift toward 0, equally in both arms. | Join conversion timestamps to first-exposure timestamps. |
| A7 | **The experiment window is unknown.** The data has no dates, only each user's peak ad day of week and hour. | No timestamps in the file. | We cannot check novelty or wear-out, seasonality, or whether the test covered full weekly cycles. The +0.77 pp is an average over an unknown period. | Request assignment and conversion timestamps and plot the lift by week. Run the next test for whole weeks (at least two) with timestamps logged (R4). |
| A8 | `total ads` = number of ad slots served to the user during the experiment. **In the PSA arm it counts PSAs**, not ads. | PSA design: the control sees a PSA in the same slot. The mean per user is the same in both arms (24.82 vs 24.76). | If it counted something else, the exposure-parity check (M13) and the ad-impression total used for CPM (14,014,701) would be wrong. | Ad-server delivery logs per arm. |
| A9 | `total ads`, `most ads day` and `most ads hour` are **post-assignment** (measured during the experiment). They are never used as covariates. | They reflect how much a user used the app while the test ran. Their distributions differ slightly by arm (Cramér's V 0.018–0.022). | Treating them as pre-treatment would turn exploratory segment lifts (e.g. by exposure) into false causal claims, and could bias adjusted estimates. | Use activity from *before* assignment (e.g. sessions in the prior 28 days) as the stratifier in the next test. |
| A10 | The PSA is a neutral placebo: same slot, size and frequency as the ad, and no effect on conversion itself. | Standard PSA / ghost-ad design. | If the PSA itself changes conversion (e.g. annoys users), the lift is over- or understated. | Add a no-ad (ghost-ad) arm next time, or compare with a pre-period baseline. |
| A11 | `most ads day` / `most ads hour` are the day of week and hour (0–23) in which the user saw the most ads, in one consistent time zone. They are not the day or hour of conversion. | Column names; no documentation. | Day-part conclusions (R3) could be shifted by hours, or could describe browsing habits rather than ad timing. | Ad-server documentation. |
| A12 | The 36 users with more than 1,000 ads (max 2,065) are real heavy users and are kept. | No rule marks them invalid. | If they are bots, the 200+ exposure bucket is contaminated. That bucket is already exploratory and has only 258 control users. | Bot / fraud filters; session data. |

## B. Business translation (ad experiment)

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| B1 | **Value per conversion = USD 50. Illustrative.** (`value_per_conversion_usd: 50`; adjustable on dashboard page 4.) | The data has no revenue or margin field. | The breakeven CPM (USD 15.49) and incremental value (USD 217,149) scale linearly with it: about USD 7.75 breakeven at USD 25, about USD 30.99 at USD 100. Incremental conversions (4,343) do not depend on it. | Finance: contribution margin (not revenue) per conversion, ideally 90-day LTV. |
| B2 | **The actual CPM paid is unknown.** | The data has no cost fields. | We cannot say whether the campaign was profitable, only below which price it would be. | Media invoices ÷ impressions served. |
| B3 | Every conversion is worth the same, incremental or not. | Simplification. | If the incremental converters are lower-value (marginal buyers), the value is overstated. | Compare order value or retention of converters between arms. |
| B4 | The measured lift carries over to a comparable future flight (same audience, creative, season and frequency). | Needed to plan with "≈ 4,343 incremental conversions per comparable flight". | Creative wear-out, seasonality or a different audience would shrink or grow the effect. | Always-on 5–10% PSA holdout (R1). |
| B5 | The breakeven covers media cost only. It excludes creative, agency and tooling costs, and the cost of the PSA impressions (a measurement cost). | These costs are not in the data. | The true breakeven CPM is lower than USD 15.49. | Full cost breakdown from Finance / Marketing. |
| B6 | Extra budget would buy more impressions on similar users at similar frequency. | The experiment did not vary budget, and the exposure dose-response is observational. | Doubling spend could mostly add impressions for users who are already saturated: the data shows no measurable lift beyond 200 ads. | Randomized 2× budget or frequency-cap test (R2). |
| B7 | A 10% relative lift is the smallest effect worth detecting in the next test. | Business judgement used for sample sizing (`ad.power.total_n_for_10pct_rel_lift`). | If smaller lifts matter, the next test needs more users than the 181,074 quoted for a 50/50 split. | Agree with the Growth PM before launch. |

## C. Cookie Cats (retention and gate experiment)

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| C1 | Cookie Cats new players stand in for "our new users" in the PM's retention question. | The ad data has no retention field, and the two datasets share no users. | Exact segment sizes and rates will not transfer; what we carry over is the pattern (Day 1 is the biggest drop, early engagement separates players). | Re-run the same cuts on our own app's install cohorts. |
| C2 | `retention_1` / `retention_7` = the player came back and played on day 1 / day 7 after install. They are point-in-time flags, not cumulative. | Dataset documentation. Consistent with the data: 3,599 raw rows have D7 without D1. | If they meant "at any time within 1 / 7 days", D7 would be a cumulative rate and benchmarks would not be comparable. | Game telemetry definitions (calendar day vs 24-hour window). |
| C3 | `sum_gamerounds` = rounds played in the **first 14 days** after install. | Dataset documentation. | The window overlaps D7, so rounds and retention partly measure the same behaviour. Rounds vs retention is correlation only, and R6 has to be tested by experiment. | Event-level play logs with timestamps. |
| C4 | The player with 49,854 rounds is a logging error and is excluded (rule: > 10,000 rounds, `gamerounds_outlier_max: 10000`). | That is ≈ 3,561 rounds per day for 14 days, which is not humanly plausible. The next-highest player has 2,961. | None for retention: D1 44.52% and D7 18.61% with or without the player. Mean rounds go from 51.87 to 51.32. | Raw event log for `user_id` 6390605. Sensitivity in [`03_data_quality_checks.md`](03_data_quality_checks.md). |
| C5 | Players were randomized **50/50** at install between gate_30 (current experience, control) and gate_40 (`intended_gate40_share: 0.50`). | Standard design; dataset description. | The observed split, 45,489 vs 44,699, gives an **SRM WARNING (p = 0.0085)**. If assignment is broken, the D7 difference could be partly or wholly an artefact. | Assignment logs by date, platform, app version and country; bot filtering. A lead: gate_40's extra players are all among players with < 30 rounds (28,876 vs 28,044), who are unlikely to have reached either gate. |
| C6 | Every player is a new install during the test and was assigned once. | Dataset description; `userid` is unique. | Returning players would raise the retention baseline. | Install dates from telemetry. |
| C7 | Rounds ≥ 30 approximates "reached the level-30 gate". | There is no level field, and each level needs at least one round. | Replays inflate rounds, so some players with ≥ 30 rounds never reached level 30. Cuts by this proxy are descriptive only. | Level-progress events. |

## S. Statistical conventions and reproducibility

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| S1 | α = 0.05 two-sided, 95% intervals, 80% power for MDE and sample size (`alpha`, `power`). | Common convention. | Labels near the edge flip: gate D1 (p = 0.074) would count at α = 0.10. Decisions rest on the intervals, not only on the label. | Pre-register α and power for the next test (R4). |
| S2 | **SRM rule:** χ² goodness of fit against the intended split. p < 0.001 = **FAIL** (stop). 0.001 ≤ p < 0.01 = **WARNING** (do not certify; investigate assignment). p ≥ 0.01 = **PASS**. | 0.001 is the usual hard threshold for SRM on large experiments; the WARNING band stops a borderline imbalance from passing silently. Implemented in `src/stats.py` `srm_check()` (`threshold` 0.001, `warn_threshold` 0.01) and `sql/03_srm_check.sql`. | With a single 0.001 cut-off, the gate test (p = 0.0085) would pass unnoticed. With a single 0.01 cut-off, it would be a hard FAIL. Under a WARNING, a decision is allowed only when it is the safe default (no change). | Align with the experimentation platform's standard. |
| S3 | Normal approximations (z-test, Newcombe and Wilson intervals) are adequate at these sample sizes. | The smaller arm has 23,524 users and 420 conversions. | Small segments are unreliable; hours 0–6 have at most 1 control conversion each. Their intervals are wide and they are not read one by one. | The bootstrap agrees with the analytic interval for the headline (0.59 to 0.95 pp vs 0.59 to 0.94 pp). |
| S4 | Bootstrap: 10,000 resamples (`n_bootstrap`) with percentile intervals. Each draw comes from the binomial at the arm's observed rate, which is equivalent to resampling user rows for a yes/no outcome. | `stats.bootstrap_two_prop()`. | Monte Carlo noise moves an interval bound by a few thousandths of a pp. A re-run with another seed can change the last rounded digit, but not the conclusion. | Re-run with another seed and compare. |
| S5 | **Random seed 20211103** for every bootstrap (`seed`). The gate experiment uses seed + 1 for D1 and seed + 7 for D7. | `config.yaml`, `src/analysis.py`. | Without a fixed seed, re-runs would move bootstrap numbers slightly. | Run the pipeline twice and diff `reports/results.json`. |
| S6 | Multiple comparisons: one family per dimension (7 days, 24 hours, 8 exposure buckets). Holm is the default, with BH and Bonferroni reported. The interaction test runs first. | Controls false alarms when scanning segments. | A different family (e.g. all 39 segments at once) would leave fewer "significant" segments. No decision relies on an individual segment. | Pre-register segment hypotheses in the next test. |
| S7 | The primary metrics were fixed before the results were looked at: conversion rate for the ad test, D7 retention for the gate test. | This is a retrospective analysis, so formal pre-registration was not possible; the metrics were fixed in [`01_request_and_scope.md`](01_request_and_scope.md) first. | Picking the metric after seeing the results inflates false positives. | Pre-register in the next test (R4). |
| S8 | Bucket cut points were set in advance. Exposure: 1–5, 6–10, 11–20, 21–35, 36–50, 51–100, 101–200, 200+. Rounds: 0, 1–4, 5–14, 15–29, 30–39, 40–99, 100+ (around the level-30 and level-40 gates). | `src/config.py`. Round numbers and gate positions, not tuned to the results. | Other cut points would change segment-level numbers. | Sensitivity check with other cuts. The dashboard's engagement curve uses every round count, with no buckets. |
| S9 | One analysis on the final data, with no interim looks. | Retrospective: only the final data exists. | Not an issue here. The next test must fix its duration in advance to avoid peeking. | Fixed duration and sample size in the next test plan (R4). |
