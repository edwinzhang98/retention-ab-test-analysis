# Assumptions Log

**Owner:** Product Analyst, Growth · **Last updated:** 2026-11-03 (v3.1: wording tightened)

Every assumption behind the numbers in this project is listed here, one per row: what we assumed, why (or where it comes from), what changes if it is wrong, and how to check it. The IDs are referenced from [`02_metric_definitions.md`](02_metric_definitions.md), [`readout.md`](readout.md), [`03_data_quality_checks.md`](03_data_quality_checks.md) and `config.yaml`. Rows that set a parameter name the `config.yaml` key. IDs never change; new rows are added at the end of each section.

## Check these first

These are the most likely to change a decision.

| ID | Why it matters |
|---|---|
| **B1, B2** | Value per conversion and the actual CPM decide whether the campaign *pays*. Today we can only state a breakeven threshold. |
| **C5, C7, C8** | The gate experiment's split gives an SRM WARNING, with the net excess among low-engagement installs. The gate result cannot be certified until assignment is explained. C7 and C8 separate "could be the gate" from "cannot be the gate", and C7's edge case is one reason the −0.32 pp is only "the part the gate could explain". |
| **A1** | The ad experiment's 96/4 allocation is inferred, not documented, and the observed split is quota-exact, so its SRM "pass" carries no information. Exposure parity carries the check. |
| **B6** | Nothing in the test measures what *extra* spend returns. The lift sits in heavy users, whose response to more ads is unknown. |
| **B7, B10, B11** | The thresholds that judge power and size the next tests (10% for the ad test, 0.5 pp of D7 for a gate re-test, +0.5 pp of D7 for the onboarding test) are placeholders until the PMs and Finance agree them. |
| **A7** | Without dates we cannot check novelty effects, test duration or seasonality. |
| **A5** | The conversion event is undocumented, so we don't know what a "conversion" is worth. |

## A. Ad experiment (Marketing A/B)

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| A1 | The intended allocation was **96% ad / 4% PSA** (`intended_ad_share: 0.96`). | Not documented in the data source; inferred from the observed split. The split is **quota-exact**: 564,577 is the nearest whole number to 96% of 588,101 (564,576.96), 0.04 users off, where independent random assignment would typically miss by about 150 users. Random assignment lands exactly there with probability 0.27%, so users were **most likely** allocated to a fixed quota, or the public file was trimmed to the ratio. Fixed arm sizes are a valid design (A2). | The SRM test (p > 0.99) passes by construction and cannot detect a broken assignment. If the design was, e.g., 95/5 or 90/10, the observed split would be a large mismatch and the result could not be certified. If the file was trimmed, we don't know which users were removed. | Get the allocation config from the experimentation platform and ask how the public export was produced. Until then, rely on exposure parity: mean ads per user are 24.82 vs 24.76 (M13). |
| A2 | Assignment was random at the user level and fixed for the whole flight (no re-assignment, no switching arms). A fixed quota is compatible with this if users were placed in random order (complete randomization). | Standard for a PSA-holdout design. `user id` is unique (588,101 rows, 0 duplicates). | Self-selection or arm switching would bias the lift in an unknown direction. | Assignment logs should show one assignment event per user, made before first exposure. |
| A3 | Users are independent: no interference between arms, and one person = one `user id`. | The user is the unit of analysis; the data has no household or device keys. | Spill-over (e.g. ad-arm users influencing PSA-arm users) shrinks the measured lift. One person under several IDs overstates precision. | De-duplicate by device / login and measure the share of people with several IDs. If spill-over is plausible, randomize in clusters. |
| A4 | The file contains every user who was *served* at least one ad slot, with the same inclusion rule in both arms. Conversion rates are therefore defined among users with at least one impression. | `total ads` ≥ 1 for every row (min = 1). | If one arm lost users differently (e.g. ad blockers affect real ads but not PSAs), the denominators differ and the lift is biased. | Reconcile assigned vs served users per arm against the ad server. |
| A5 | `converted` is a yes/no flag per user for one business event (e.g. purchase or sign-up; not documented). It is measured the same way in both arms and counted at most once per user. | The only values are `True` / `False`; the data has no event name and no counts. | The value per conversion (B1) could be off by an order of magnitude. Repeat conversions are invisible, so impact is undercounted if ads drive repeat purchases. | Check the tracking plan / event dictionary with the data owner, and whether upstream has more than one conversion per user. |
| A6 | Only conversions after assignment and within the experiment window are counted. | Standard for an experiment outcome; there are no timestamps to check it. | Pre-exposure conversions would dilute the lift toward 0, equally in both arms. | Join conversion timestamps to first-exposure timestamps. |
| A7 | **The experiment window is unknown.** The data has no dates, only each user's peak ad day of week and hour. | No timestamps in the file. | We cannot check novelty or wear-out, seasonality, or whether the test covered full weekly cycles. The +0.77 pp is an average over an unknown period. | Request assignment and conversion timestamps and plot the lift by week. Run the next test for whole weeks (at least two) with timestamps logged (R4). |
| A8 | `total ads` = number of ad slots served to the user during the experiment. **In the PSA arm it counts PSAs**, not ads. | PSA design: the control sees a PSA in the same slot. The mean per user is the same in both arms (24.82 vs 24.76). | If it counted something else, the exposure-parity check (M13) and the ad-impression total used for CPM (14,014,701) would be wrong. | Ad-server delivery logs per arm. |
| A9 | `total ads`, `most ads day` and `most ads hour` are **post-assignment** (measured during the experiment). They are never used as covariates or strata for an effect estimate. | They reflect how much a user used the app while the test ran, and ads can change how long a user stays from the first impression, so exposure can itself be caused by treatment. Their distributions differ slightly by arm: 33.4% of PSA vs 30.1% of ad users saw 1–5 ads, and 17.6% vs 21.8% saw 11–20 (KS D = 0.040; Cramér's V 0.018–0.022). We can't tell whether that comes from PSA delivery or from ads changing behaviour. Contrast with the gate test's rounds bands (C8). | Treating them as pre-treatment would turn exploratory segment lifts (e.g. by exposure, M4a) into false causal claims, and could bias adjusted estimates. | Use activity from *before* assignment (e.g. sessions in the prior 28 days) as the stratifier in the next test (R2). |
| A10 | The PSA is a neutral placebo: same slot, size and frequency as the ad, and no effect on conversion itself. | Standard PSA / ghost-ad design. | If the PSA itself changes conversion (e.g. annoys users), the lift is over- or understated. | Add a no-ad (ghost-ad) arm next time, or compare with a pre-period baseline. |
| A11 | `most ads day` / `most ads hour` are the day of week and hour (0–23) in which the user saw the most ads, in one consistent time zone. They are not the day or hour of conversion. Dayparts group that hour into Night (0–5), Morning (6–11), Afternoon (12–17) and Evening (18–23). They describe **when the user was most exposed, i.e. the user's habits**, recorded after assignment, not a slot a media buyer can buy. | Column names; no documentation. | Day-part conclusions could be shifted by hours. Even if the fields are exactly right, "Tuesday-peak users respond more" does not mean "ads bought on Tuesday work better", which is why R3 asks for a pre-registered test that randomizes the delivery schedule (weekday and time slot). | Ad-server documentation; the randomized delivery-schedule test (R3). |
| A12 | The 36 users with more than 1,000 ads (max 2,065) are real heavy users and are kept. | No rule marks them invalid. | If they are bots, the 200+ exposure bucket is contaminated. That bucket gives no usable estimate anyway (95% CI −4.93 to +4.10 pp, 258 control users). | Bot / fraud filters; session data. |

## B. Business translation and decision thresholds

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| B1 | **Value per conversion = USD 50. Illustrative.** (`value_per_conversion_usd: 50`; adjustable on the dashboard's Overview and Experiment Readout pages.) | The data has no revenue or margin field. | The breakeven CPM (USD 15.49), the incremental value (USD 217,149) and the holdout's cost in money (USD 11,310) scale linearly with it: the breakeven is about USD 7.75 at USD 25 and about USD 30.99 at USD 100. Incremental conversions (4,343) do not depend on it. | Finance: contribution margin (not revenue) per conversion, ideally 90-day LTV. |
| B2 | **The actual CPM paid is unknown.** | The data has no cost fields. | We cannot say whether the campaign was profitable, only below which price it would be. | Media invoices ÷ impressions served. |
| B3 | Every conversion is worth the same, incremental or not. | Simplification. | If the incremental converters are lower-value (marginal buyers), the value is overstated. | Compare order value or retention of converters between arms. |
| B4 | The measured lift carries over to a comparable future flight (same audience, creative, season and frequency). | Needed to plan with "≈ 4,343 incremental conversions per comparable flight" and to cost the holdout (M18). | Creative wear-out, seasonality or a different audience would shrink or grow the effect. | The always-on 5% PSA holdout (R1, B8) re-measures it every flight. |
| B5 | The breakeven covers media cost only. It excludes creative, agency and tooling costs, and the cost of the PSA impressions (a measurement cost). | These costs are not in the data. | The true breakeven CPM is lower than USD 15.49. | Full cost breakdown from Finance / Marketing. |
| B6 | Extra budget would buy more impressions on similar users at similar frequency. | The experiment did not vary budget, and the exposure pattern is observational: exposure tracks how active a user is (PSA conversion rises from 0.28% at 1–5 ads to 15.50% at 200+). | Extra spend could go to light users, where there is no lift we could measure (the 66% of all users with ≤ 20 ads), or to heavy users, whose response at higher frequency is unknown (98% of the bucket-by-bucket incremental conversions come from the 17% of ad users with 36–200 ads, M4a; the 200+ bucket is unusable). The return on 2× spend could be much lower than today's average. | A user-level test with an up-to-2× impressions arm or a frequency cap; a geo split for a true budget test (R2). |
| B7 | **A 10% relative lift is the smallest lift worth acting on** (`smallest_lift_of_interest_rel: 0.10`; 0.18 pp at the 1.79% PSA baseline, about 1,008 conversions per 565K-user ad flight, about USD 50K at USD 50). Power is judged at this lift, never at the observed effect (M14). | **A placeholder assumption in `config.yaml`.** In practice the Growth PM and Finance agree this number before launch; no such number was recorded for this test, so we assumed one. Used to judge this test's power and to size the next test (`ad.power.power_at_relative_lift`, `ad.power.total_n_for_10pct_rel_lift`). | At 96/4 this test had 50.8% power for that lift (≈100% if the same users had been split 50/50). If smaller lifts matter, the next test needs more than the 181,074 users quoted for a 50/50 split. | Agree the threshold with the Growth PM and Finance before the next launch (R4). |
| B8 | **Always-on holdout share = 5%** (`holdout_share: 0.05`). | A balance between precision and cost: a 5% holdout is slightly larger than this test's 4% PSA arm, so each flight's read is about as precise as this test's, at a cost of ≈ 226 conversions per 588K-user flight (≈ USD 11.3K at USD 50) vs no holdout. This test's 4% PSA arm already forgoes ≈ 181, so the step from 4% to 5% costs ≈ 45 more (M18). | A smaller holdout gives noisier reads per flight; a larger one forgoes more conversions. | Agree with the Growth PM; revisit after two flights. |
| B9 | The last-touch comparison assumes a last-touch model would credit **all 14,423 ad-arm conversions** to the campaign. Every ad-arm user saw at least one ad, so last-touch and any-touch credit coincide here. | Simplest benchmark; the data has no channel or touchpoint information. | If other channels take part of that credit, the overstatement is smaller than 3.3× (95% CI 2.7× to 4.3×; M5). | Compare with the attribution report the team actually uses. |
| B10 | **Smallest D7 change worth acting on in a gate re-test = 0.5 pp per install** (`gate_smallest_d7_change_pp: 0.5`; about 2.6% of gate_30's 19.02% D7). | **A placeholder to agree with the Game PM** before any re-test. It is fixed in advance so that the re-test is never sized at the observed gap (M14). Among players who reach level 30 it equals 1.36 pp on their 43.87% D7 (0.5 pp ÷ the 36.89% who reach level 30). | It sets the re-test size: 191,453 installs at 50/50 if analysed over all installs, or 41,933 players who reach level 30 (≈ 113,669 installs) with the pre-registered reacher analysis (M14). These sizes detect a 0.5 pp drop; a rise of the same size needs slightly more: ≈ 2% more install-level (≈ 195K) and ≈ 0.7% more for the reacher analysis (≈ 114.4K installs). The reacher figure uses this cohort's 36.89% reaching level 30; re-check with the new cohort's share before launch. A smaller threshold needs more installs. A true effect smaller than the threshold would not change the decision. | Agree with the Game PM which D7 change would change the gate decision, before the re-test is designed (R5). |
| B11 | **Onboarding test target = +0.5 pp of D7 among players with < 15 rounds** (`onboarding_target_lift_pp: 0.5`). | **A placeholder** for sizing R6, on the segment's own 2.27% D7 (not all installs' 18.61%). | It sets the R6 size: 30,809 target players ≈ 65,648 installs at 50/50 (M23). A smaller target needs more players. If the real targeting rule (first-day play) picks a segment with a different base rate, the size changes. | Agree the target with the Onboarding PM; re-size once first-day play defines the segment (R6). |

## C. Cookie Cats (retention and gate experiment)

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| C1 | The retention analysis uses the company's **mobile game, Cookie Cats** (one 2017 install cohort), a different product from the app the ads ran in. Its *pattern* carries over to the app's new users; its exact segment sizes do not. | The ad data has no retention field, and the two products share no users. The game's own decisions sit with the Game PM (R5) and the Onboarding PM (R6), colleagues at the same company. | Exact segment sizes and rates will not transfer one-for-one; what we carry over is the pattern (Day 1 is the biggest drop, early engagement separates players). | Re-run the same cuts on the app's own new installs. |
| C2 | `retention_1` / `retention_7` = the player **came back to the game** on day 1 / day 7 after install. They are classic day-N flags (activity on that day), not rolling and not cumulative. A return does not require a finished round: 87 of the 3,994 zero-round players are flagged on Day 1 and 29 on Day 7 (111 on either, 0.12% of players). | Dataset documentation. Consistent with the data: 3,599 raw rows have D7 without D1. | If they meant "at any time within 1 / 7 days", D7 would be a cumulative rate and benchmarks would not be comparable. The zero-round flags are about 0.1% of players; no conclusion depends on them. | Game telemetry definitions: calendar day vs 24-hour window, and what counts as a return. |
| C3 | `sum_gamerounds` = rounds played in the **first 14 days** after install. | Dataset documentation. | The window overlaps D7, so rounds vs retention is partly definitional: it sizes the early-churn segment (M23) but is not a Day-0 targeting rule, and R6 has to be tested by experiment. | Event-level play logs with timestamps (first-day rounds). |
| C4 | The player with 49,854 rounds is a logging error and is excluded (rule: > 10,000 rounds, `gamerounds_outlier_max: 10000`). | That is ≈ 3,561 rounds per day for 14 days, which is not humanly plausible. The next-highest player has 2,961. | None for retention: D1 44.52% and D7 18.61% with or without the player. Mean rounds go from 51.87 to 51.32. The SRM checks still count the player, because they use raw assignment counts (S2). | Raw event log for `user_id` 6390605. Sensitivity in [`03_data_quality_checks.md`](03_data_quality_checks.md). |
| C5 | Players were randomized **50/50** at install between gate_30 (current experience, control) and gate_40 (`intended_gate40_share: 0.50`). | Standard design; dataset description. | The raw assignment counts, 44,700 vs 45,489, give an **SRM WARNING (p = 0.0086)**. gate_40 has ≈ 790 extra players (789 in the raw counts). By rounds band (raw counts), there is a net excess of 762 among players with < 15 rounds (p = 0.0002). At 15–29 rounds the net excess is +70 (p = 0.56), and players with 30+ rounds are balanced, −43 (p = 0.81). These bands were chosen after the warning, so their p-values are descriptive (M19). If assignment or logging is broken, the D7 difference is partly or wholly an artefact (M19–M21). | Assignment logs by date, platform, app version and country; duplicate-install and bot filtering; whether either version failed to log players who left at once. |
| C6 | Every player is a new install during the test and was assigned once. With no install dates, all players are treated as **one install cohort**. | Dataset description; `userid` is unique. | Returning players would raise the retention baseline. No comparisons by install date, trends or seasonality are possible. | Install dates from telemetry. |
| C7 | 30+ rounds means **"could have reached level 30"**. It rests on **rounds ≥ levels**: each level takes at least one round, and replays only add rounds. | There is no level field. | Under the assumption, a player with < 30 rounds cannot have got past level 30, but 30+ rounds does not guarantee reaching it (replays), so cuts by the 30+ proxy are blurred. **Edge case:** a gate_30 player who clears levels 1–29 in exactly 29 rounds (no replays) meets the level-30 gate with 29 rounds and, if they stop there, sits in the < 30 band. Such players are few: there is no pile-up at 29 rounds (311 gate_40 vs 302 gate_30 players), and excluding everyone with 29 rounds, the 15–28 band still shows a D7 gap of −0.68 pp (95% CI −1.64 to +0.28). So the strata are close to, not exactly, gate-free. If levels can be skipped (e.g. bought), even the < 30 side fails. | Level-progress events; confirm with the game team that levels cannot be skipped. |
| C8 | **Negative-control logic.** The two versions are identical until level 30, and, given rounds ≥ levels (C7), a player with < 30 rounds cannot have got past level 30. So neither gate can influence (a) whether a player ends up with < 30 rounds, (b) the retention of players with < 30 rounds, or (c) play before round 30 (`min(rounds, 29)`). Under a fair 50/50 split all three should match between versions. This is also why the rounds bands can be used as strata although total ads cannot (A9): ads can change behaviour from the first impression, while whether a player ever plays 30 rounds cannot depend on the gate, so it behaves like a pre-treatment trait. | Game design plus C7. Used by M19 (SRM by rounds band), M20 (decomposition) and M21 (negative controls). It is an approximation; its known gap is the C7 edge case. | If players can see or anticipate the gate's position before reaching it (e.g. on a level map), behaviour before level 30 could differ for a real reason, and the controls would be weaker evidence of an assignment or logging problem. | Confirm with the game team what players see before level 30; level-progress events. |
| C9 | A gate effect, if any, acts only on players who reach level 30. The install-level part the gate could explain is the reachers' D7 difference × the share reaching 30 (36.89% on average). | Follows from C8: players who never reach level 30 never meet a gate. | It is the part the gate could explain, not an estimate of the gate's effect: players with 15–29 rounds, who never met a gate, show a similar D7 gap (−0.87 pp, 95% CI −1.82 to +0.07) to players with 30+ rounds (−0.87 pp, 95% CI −1.94 to +0.20; M21), so even the −0.32 pp in M20 may not be the gate. If the gate's position changed behaviour before level 30 (C8), part of the never-reached difference could be a real gate effect instead. | Level-progress events in any re-test; pre-register D7 among players who reach level 30 as the primary analysis (R5, B10). |

## S. Statistical conventions and reproducibility

| # | Assumption | Why / source | Impact if wrong | How to validate |
|---|---|---|---|---|
| S1 | α = 0.05 two-sided, 95% intervals, 80% power for MDE and sample size (`alpha`, `power`). | Common convention. | Labels near the edge flip: gate D1 (p = 0.074) would count at α = 0.10, and the D7 negative control (p = 0.049) would not count at α = 0.01. Decisions rest on the intervals, not only on the label. | Pre-register α and power for the next test (R4). |
| S2 | **SRM rule:** χ² goodness of fit of the **raw assignment counts** against the intended split. p < 0.001 = **FAIL** (stop), the threshold used by Kohavi et al. (*Trustworthy Online Controlled Experiments*). 0.001 ≤ p < 0.01 = **WARNING** (do not certify; investigate assignment), a **project convention**. p ≥ 0.01 = **PASS**. (`srm_fail_p: 0.001`, `srm_warn_p: 0.01`.) | 0.001 is the usual hard line for SRM on large experiments; the WARNING band stops a borderline imbalance from passing silently. Raw counts are used because assignment precedes cleaning. Implemented in `src/stats.py` `srm_check()` and `sql/03_srm_check.sql`. | With only the 0.001 line, the gate test (p = 0.0086) would pass unnoticed; with only a 0.01 line, it would be a hard FAIL. The WARNING band is our choice, not an industry standard. Under a WARNING, a decision is allowed only when it keeps the status quo. Subsets chosen after the result (M19) get no status: their p-values are descriptive and don't change the experiment-level status. | Align with the experimentation platform's standard. |
| S3 | Normal approximations (z-test, Newcombe and Wilson intervals) are adequate at these sample sizes. | The smaller arm has 23,524 users and 420 conversions. | Small segments are unreliable: 6 hours (0–2 and 4–6, mostly night) have 0 control conversions, and the Night daypart has 1 among 735 users. Their intervals are wide, they are not read one by one, and contrasts use Agresti–Caffo variances for their CI and p (S10). | The bootstrap agrees with the analytic interval for the headline (0.59 to 0.95 pp vs 0.59 to 0.94 pp). |
| S4 | Bootstrap: 10,000 resamples (`n_bootstrap`) with percentile intervals for yes/no metrics. Each draw comes from the binomial at the arm's observed rate, which is equivalent to resampling user rows for a yes/no outcome. Rounds played use a user-level bootstrap with 2,000 resamples (`n_bootstrap_means`). | `stats.bootstrap_two_prop()`, `stats.bootstrap_mean_diff()`. | Monte Carlo noise moves an interval bound by a few thousandths of a pp. A re-run with another seed can change the last rounded digit, but not the conclusion. | Re-run with another seed and compare. |
| S5 | **Random seed 20211103** for every bootstrap (`seed`). The gate experiment uses seed + 1 for D1, seed + 7 for D7, seed + 14 / + 15 for the all-player rounds bootstraps and seed + 16 for rounds among players with 30+ rounds. | `config.yaml`, `src/analysis.py`. | Without a fixed seed, re-runs would move bootstrap numbers slightly. | Run the pipeline twice and diff `reports/results.json`. |
| S6 | Multiple comparisons: one family per dimension (7 days, 24 hours, 4 dayparts, 8 exposure buckets), adjusted separately for the segment-vs-rest contrasts and for the per-segment lift tests. Holm is the default, with BH and Bonferroni reported. The interaction test runs first; because 3 dimensions were explored (day, hour, exposure; the daypart regroups the hour), the day result is also shown × 3 (0.038). | Controls false alarms when scanning segments. Per-segment "lift ≠ 0" counts measure power, not heterogeneity, so they are never used as heterogeneity evidence (M15). | A different family (e.g. all 43 segments at once) would leave fewer "significant" segments. No decision relies on an individual segment. | Pre-register segment hypotheses in the next test. |
| S7 | The primary metrics were fixed before the results were looked at: conversion rate for the ad test, D7 retention for the gate test. The v2 and v3 diagnostics (M4a, M17–M23, the daypart cut, the rounds bands) were added after the first results, as methods checks. | This is a retrospective analysis, so formal pre-registration was not possible; the primary metrics were fixed in [`01_request_and_scope.md`](01_request_and_scope.md) first. | Picking the metric after seeing the results inflates false positives. The diagnostics are read as checks on the primary results, not as new findings, and their subsets carry no PASS / FAIL labels. | Pre-register in the next test (R4). |
| S8 | Bucket cut points were set in advance. Exposure: 1–5, 6–10, 11–20, 21–35, 36–50, 51–100, 101–200, 200+. Rounds: 0, 1–4, 5–14, 15–29, 30–39, 40–99, 100+ (around the level-30 and level-40 gates); the gate's rounds bands (< 15, 15–29, 30+) reuse these cut points. Dayparts (added in v2) are plain 6-hour blocks of the clock, not tuned to the results. | `src/config.py`. Round numbers and gate positions, not tuned to the results. | Other cut points would change segment-level numbers. | Sensitivity check with other cuts. The dashboard's engagement curve uses every round count, with no buckets. |
| S9 | One analysis on the final data, with no interim looks. | Retrospective: only the final data exists. | Not an issue here. The next test must fix its duration in advance to avoid peeking. | Fixed duration and sample size in the next test plan (R4). |
| S10 | Segment-vs-rest contrasts use **Agresti–Caffo** adjusted proportions (one success and one failure added per group) **for the confidence interval and the p-value only**. The point estimate is the raw difference, `abs_lift − lift_rest`. | With plain proportions a cell with 0 control conversions has zero variance and can look "significant" by accident; 6 hours (0–2 and 4–6, mostly night) have 0 control conversions. The raw point estimate keeps the contrast equal to the difference of the lifts shown in the tables. | In sparse cells the CI is not centred on the point estimate (Night: +0.45 pp, CI −0.12 to +0.77; CI centre (adjusted) +0.32 pp, `diff_vs_rest_ac` in the tables), and the adjustment makes small-cell contrasts more conservative. For large segments the two centres agree closely: across the 7 peak days they differ by at most 0.03 pp. | Compare with an exact or score-based interval for the contrast. |
| S11 | Stratified analyses on post-assignment strata (Mantel–Haenszel risk difference; CMH) are **sensitivity checks**, not adjusted effects. | The strata (day, hour, daypart, exposure) are post-assignment (A9). | Presenting a pooled odds ratio as "the adjusted effect" would mislead. As a check, the stratified lift is 0.76–0.81 pp vs 0.77 pp crude: no Simpson reversal. | Use pre-assignment strata in the next test. |
| S12 | The gap decompositions (D7 and D1, M20) use **symmetric weights**: the average of the two arms' shares for the within-stratum part and the average of their rates for the composition part. | Gives an exact split with no residual and treats neither arm as the reference (M20). | Using either arm's shares as weights instead moves the parts by less than 0.01 pp; the could-be-the-gate part stays −0.32 pp for D7 and +0.03 pp for D1. | Recompute with control-arm or treatment-arm weights. |
| S13 | Derived numbers are computed from the unrounded values in `reports/results.json` (8 decimals), never from rounded ones. | Rounding twice can move a last digit, e.g. the D7 upper bound among players with 30+ rounds is +0.20 pp from the stored value. | A stale or double-rounded number would disagree with the pipeline in its last digit. | Recompute any derived number from `reports/results.json` and `reports/tables/*.csv`, not from a number rounded for a document. |
